Onote Generation Logic

This document guides the note generation process. When /onote is invoked, follow these steps:

Step 1: Analyze the Conversation

Review the full conversation history and extract:

  1. What was the user trying to learn or solve? (The problem statement)
  2. What questions did they ask? (The conversation flow)
  3. What answers did you provide? (The content)
  4. What shifted their understanding? (Key “aha” moments)
  5. What decisions did they make? (Architecture, tool, approach choices)

Step 2: Identify Learnings Using the Significance Criteria

Apply the Significance Checklist from SKILL.md:

✅ Keep if: New concept, changed approach, solved problem, reusable tool/command, mental model shift
❌ Skip if: Confirmation of known info, meta-commentary, minor clarifications

For each significant learning, extract:
- The core insight (1–2 sentences)
- Key details (bullet points)
- Confidence level (Confirmed/Provisional/Hypothesis)
- Code example or command (if applicable)
- References (links, docs)
- Gotchas or caveats

Step 3: Identify Decisions Made

Look for points where the user:
- Chose between multiple options
- Decided to pursue a specific approach
- Rejected an alternative (and why)

Capture in the Decisions Made table:

| Decision | Chosen | Rejected | Reason |
|----------|--------|----------|--------|

Step 4: Extract Concrete Artifacts

For every learning, pull:
1. Code snippets — minimal executable examples
2. Commands — with flags and explanation
3. Links — GitHub, docs, tutorials, StackOverflow
4. Gotchas — edge cases, version quirks, preconditions

If a learning has no artifacts (e.g., “I now understand X concept”), that’s OK — focus on explanation and references.

Step 5: List Unresolved Questions & Next Steps

Scan the conversation for:
- Questions that remain open (“I wonder if…”)
- Follow-up work (“I still need to test…”)
- Actions the user should take next
- Experiments to validate provisional learning

Step 6: Assess Overall Confidence

Assign an overall confidence level to the note:
- high: Most learnings are [Confirmed] or [Provisional] with clear next steps
- medium: Mix of [Confirmed], [Provisional], and some [Hypothesis]
- low: Mostly [Hypothesis]; needs real-world validation

Step 7: Determine Tags

Suggest 3–5 relevant tags for Obsidian filtering. Examples:
- session-summary (always include)
- Domain tags: rust, hardware, networking, macOS, python, etc.
- Specific tool/library: hidapi, tokio, UniFi, etc.
- Focus area: reverse-engineering, optimization, debugging, etc.

Step 8: Suggest Related Notes

If the session spans multiple distinct domains, suggest creating separate notes:
- “Rust async patterns” → separate from “macOS file permissions” if both came up
- Link them via the related: field in YAML frontmatter

Step 9: Generate the Markdown File

Use this template:

---
tags: [session-summary, tag1, tag2, tag3]
date: YYYY-MM-DD
related: [[related-note-1]], [[related-note-2]]
status: raw
confidence: {high|medium|low}
---

Step 10: Save & Present

  1. Generate the filename: {Topic}-{YYYY-MM-DD}.md (kebab-case topic)
  2. Examples: spacemouse-hardware-2025-06-05.md, rust-async-patterns-2025-06-05.md
  3. Save to /mnt/user-data/outputs/
  4. Present the file path to the user
  5. Optionally, suggest how to refine or split the note

Quality Checks

Before generating, verify:

  • [ ] Title is clear — Someone reading the title should immediately know what the note covers
  • [ ] 3–5 learnings — Not too many (overwhelming) or too few (too surface-level)
  • [ ] Each learning has an artifact or reference — Not just abstract concepts
  • [ ] Decisions are explicit — Why was A chosen over B?
  • [ ] Confidence is honest — Don’t mark [Confirmed] if you only tested once
  • [ ] Next steps are concrete — Not “learn more about X” but “read the Tokio docs section 4.2 on spawning”
  • [ ] Tags are useful — Can be filtered/searched in Obsidian later

Customization: User Overrides

If the user provides a /onote prompt with qualifiers:

  • /onote focus on Rust patterns — Exclude other topics; create a tightly focused note
  • /onote separate hardware and software — Generate two linked notes instead of one
  • /onote minimal; just the top 3 learnings — Strict 3-learning limit, no filler

Adjust the generation accordingly.
